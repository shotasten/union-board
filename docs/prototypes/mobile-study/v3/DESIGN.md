# v3：予定・場所・人数を共通の入口にする

更新日：2026-11-15。 [触れる試作](./index.html) ／ [開き方](./README.md) ／ [検証記録](./VALIDATION.md)

## 今回、設計の軸として受け取ったこと

UnionBoardの最初の価値は、**いつ・どこで予定があり、何人来るのかを日程横断で把握できること**。メンバーの○△×は、その人数を構成する実情・根拠を読むためにある。自分の入力を楽にすることや人の比較を中心にして、この入口を失ってはいけない。

前の試作は「人をどう比べるか」「入力をどう分離するか」に寄り、場所と全体人数を主表から落としていた。今回は独立した案をさらに増やすのではなく、共通の予定一覧に、目的に応じて情報を重ねる構造へ改める。

| 層 | 残す情報と操作 | 閲覧者 |
|---|---|---|
| 共通の予定一覧 | 日付・曜日・イベント名・時刻・会場／部屋・○人数／△人数。12件を同じ列構成で並べる | 指揮者も演奏者も共通 |
| 自分の回答を重ねた一覧 | 上の情報を残し、選んだ本人の○△×-と入力入口を追加 | 演奏者として使う時。指揮者本人も利用 |
| 日程の内訳 | 同じ日程・場所・人数を文脈に、8パートの人数と全員の回答への入口 | パートの偏りや人数の根拠を調べる時 |
| 個人の回答 | パートを選んで各メンバーの○△×-を読む／全40人を読む／一人の12回を見る | 誰が来るか、日程を跨いだ参加状況を確認する時 |

「指揮者としてログイン」「演奏者としてログイン」という役割・権限切替は設けない。同じ人が両方の用事を持つため、**表示する情報の切替**として「予定・人数」「自分の回答」を置く。

## 1. 共通の入口：予定・人数

横スクロール不要の3列の表とする。

| 日程・時刻 | 場所 | ○／△人数・内訳 |
|---|---|---|
| 11/28（土） 練習 13:00–17:00 | 南大沢文化会館・第2練習室 | ○18人／△3人 |

カードを主ビューにはしない。イベントを行にして、同じ場所に日付・会場・人数が並ぶ一覧性を守る。説明文・検索条件・常設の入力帯で初画面を押し下げない。名前を選ばずに閲覧できる。

390×844 CSS pxでは、先頭から7イベントを完全に表示できることを確認した。全12件を1画面に詰めることよりも、場所と時刻が読めることを優先している。場所の文字サイズは、同じ画面幅で「自分の回答」に切り替えても維持する。

### 「何人来る」の定義を曖昧にしない

既定は **○と△を分ける**。11/28なら○18人と△3人を同じセルに表示する。△は遅刻・早退なので、常に21人が揃うことを意味しない。

比較用として、ページ下部の「試作の比較設定・説明」で **参加予定21人＝○18＋△3** に切り替えることもできる。後者は全体の規模を速く読めるが、練習中に同時にいる人数と誤解しやすい。表示方法はまだ決定していない。

集計の0件は現行と同じ「-」で表示。未回答と未定も現行同様に区別しない。必要な編成や必要人数はデータにないので、「足りている／足りない」「合奏できる」といった判定は追加しない。

## 2. 指揮者として：全体人数から実情へ

人数のボタンを押すと、その日程の内訳へ進む。

1. 8パートそれぞれの○△×-の人数を読む。
2. パートを押すと、そのパートの各メンバーの記号を読む。
3. 「全40人の○△×を見る」は内訳の冒頭に置く。パートを一つずつ開かなくても、人数の根拠を読めるようにする。
4. 名前から、その人の全12日程を確認する。
5. コメントもその日程の内訳から読む・書く。

人数は独立したダミーの数字ではなく、**同じ40人の回答から集計する**。本人の回答を変更した時は、一覧の全体人数・パートの人数・本人の記号が一緒に更新される。

日程を跨いだ任意のメンバー比較が必要な場合に備え、**「全12日程×40人の表」も残す**。表示専用の横長表で、日程・会場・人数の列は横スクロール中も固定する。今回の案は、人ごとの○△×を機能から削除する提案ではない。

### 比較できる2つの開き方

同じデータ・同じ内訳を使い、一覧下部の比較設定から切り替える。

| 開き方 | 良い点 | 犠牲・注意点 | 向いていそうな場面 |
|---|---|---|---|
| 行内に展開（既定） | 見ていた予定の直下で確認でき、前後の日程とのつながりが残る。閉じれば元の行へ戻る | パート8件やメンバー40人を開くと、その下の日程が遠くなる。複数日を同時に開くと長くなるため、試作は1日だけ展開 | その日のパート人数を短く確認したい時 |
| 詳細画面へ移動 | 人名・コメントなど、縦に長い情報を読みやすい。上に日程・時刻・会場・全体人数を再掲する | 一覧の前後関係は見えなくなり、戻る操作が必要 | その日の参加者やコメントをじっくり確認する時 |

詳細画面では「予定一覧へ」とブラウザの戻るの両方を使える。戻った時には一覧の表示目的とスクロール位置を復帰する。

**未決定**：まずパート人数を行内で見せ、全員名簿やコメントは詳細画面へ進める混合方式も考えられる。試作ではまず行内／詳細画面を分けて、どこから行内が長すぎると感じるか比較する。

## 3. 演奏者として：同じ一覧に、自分の回答を重ねる

「自分の回答」へ切り替えても、日程・場所・全体人数の列を残す。その右に自分の○△×-を追加する。比較対象を3人に限定したり、全体人数を隠したりしない。

本人がまだ分からない場合でも一覧は表示する。回答したい時に既存名簿から対象を選び、任意でこの端末に記憶する。保存するのは名前ではなくメンバーID。ログイン・本人確認ではなく、回答先の選択として扱う。パートを含む名前をヘッダーと入力画面に表示する。

- **1件だけ変更**：その日の自分の記号→入力画面→○△×-→保存。
- **未定を埋める**：「未定3件を入力」→2/6・2/14・2/20を同じ入力画面で表示→3件を選ぶ→保存。
- **他の日程もまとめて変更**：「まとめて変更」または入力画面内の「全12日程」。

入力画面にも、各日程の会場・時刻・全体人数を残す。4つの選択肢は44px以上。選択すると自動的に次の日へ送らず、3件を並べて見直せる。人数の下書きプレビューも表示し、保存前に確かめられる。

入力は下書き→端末内保存。取消が可能。途中で閉じても、そのページ内では再開できる。未保存の回答・コメントがある間は、別の人へ対象を変更できない。ページを再読込した場合の未保存下書きの復元は実装していない。

常設の本人用入力帯は置かない。入力していない時は、予定を読むための画面面積を返す。

## 今回の比較・検証

| タスク | 現時点で確認した経路・操作数 | 未確認のこと |
|---|---|---|
| いつ・どこ・何人 | 選択や横スクロールなしで予定一覧を見る。2表示とも12行を保持 | 読み取る速さ、会場名の大きさが本人に十分か |
| パート別人数 | 人数を1タップ | 行内8行を読む時に前後の予定が遠くならないか |
| 誰が来るか | 人数→パート、または人数→全40人の○△×。計2タップ | 元の表で名前列を追うより分かりやすいか |
| 特定の人の全12回 | 人名から12回、または一覧下部の人検索 | 一覧下部の入口を見つけられるか |
| 未定3件を別々に回答 | 対象選択済み・自分の回答表示から、開く1＋回答3＋保存1＝5タップ | 初回の名簿選択・ネイティブselectの操作時間は別途必要 |
| コメント | 人数→コメントの2タップで読む。選択済みなら同じ画面で書く | コメントへの入口が十分に目に入るか |

回答3件＋保存の4クリックは、自動操作で1.157秒だった。開く・本人選択・読む／考える時間を含まず、人の所要時間ではない。ビューの優劣をこの秒数で決めない。

320〜400pxで横はみ出し、44px以上の操作、一覧と内訳の整合性、保存・取消・途中再開、詳細からの戻るを確認した。実機のタッチ・Safari・文字拡大・スクリーンリーダーは未確認。 [詳しい記録](./VALIDATION.md)

## ガイダンスの適用

導入済みのModern Web Guidance 1.0.0で、`responsive data table`、`expand disclosure content`、`accessible modal dialog`を検索し、`responsive-table`・`content-first-noise-reduction`・`dialog`を取得して全文を読んだ。

- `responsive-table`：予定はネイティブtable。横長の原表には名前付き・フォーカス可能なスクロール領域と固定列を使う。カード化は制約に従い採用しない。
- `content-first-noise-reduction`：最初に予定を置き、比較設定は閉じたdetailsへ。常設の入力帯や大きな説明ブロックを撤去。人数を調べたい時にだけ二次情報を開く。
- `dialog`：入力・本人選択・コメントにネイティブdialogを使用。背景のinertやフォーカス閉じ込めは標準動作に任せ、閉じるボタンとEscを提供する。

新しい必須APIや依存は追加していない。`closedby`・popover・スクロール方向クエリは今回の成立条件にしない。スキルの固定元と導入は前回の記録を維持する。

## 次に議論したい点

この共通一覧を、新しい検討の基準にしたい。パートを最初から全画面に出すことよりも、まず予定・場所・人数を守る。

1. 「何人来るか」は○と△の別表示がよいか、○＋△の参加予定人数を大きく見せたいか。
2. 内訳は行内で見たいか、詳細画面で見たいか。パート人数までは行内、各メンバーからは別画面がよいか。
3. 自分の記号を追加する切替で十分か。それとも自分を記憶した後は、最初から「自分の回答」を開きたいか。
4. メンバーの○△×を今回の位置に残すことで、元の出欠表の価値が保たれているか。全員の原表への入口をもっと上に置くべきか。
